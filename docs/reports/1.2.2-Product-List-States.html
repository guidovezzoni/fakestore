User Story

Product List States — Implement loading, error, and empty states for the product list screen with proper error handling, retry functionality, and localised UI messaging.

Branch Created

feature/1.2.2-product-list-states

Refinement Summary

Description & Scope

The story refines the product list screen to handle all possible states when fetching products from the API:

  • Loading state with progress indicator
  • Content state displaying the product list
  • Empty state when no products are available
  • Error state with user-friendly messaging and retry button

Acceptance Criteria (11 items)

  1. Loading state displays a centered progress indicator
  2. Content state displays a list of products
  3. Empty state displays a message indicating no products are available
  4. Error state displays a user-friendly error message
  5. Error messages must not leak technical details (no stack traces or raw API errors)
  6. Error state includes a "Retry" button to re-fetch products
  7. Empty state is treated as a sub-case of Content state in the type hierarchy
  8. All UI strings are localised (English and Spanish)
  9. Top app bar remains visible in all states
  10. Product List State is sealed type with Loading, Content, and Error cases
  11. Retry functionality dispatches a RetryClicked intent

Type Structure Defined

ProductListUiState sealed type replaces flat data class:

  • Loading — shown during initial fetch or after retry
  • Content — shown when products loaded (includes empty product list)
  • Error — shown when fetch fails, with retry capability

MVI Contract Updates

New intent added: RetryClicked — dispatched when user taps the retry button in error state.

String Resources (3 new)

  • Error message prompt (EN + ES)
  • Retry button label (EN + ES)
  • Empty state message (EN + ES)

Non-Functional Considerations

Security: Error messages must not leak technical details (stack traces, raw API responses, internal state).

Performance: Rapid retry clicking could launch concurrent fetch requests — ViewModel must debounce or queue retry attempts.

GDPR: No personal data involved. Logging must not capture user-identifying information.

Accessibility: Loading indicator must have proper content description. Error UI must be keyboard-navigable and screen-reader friendly.

AC-8 Deviation

The user story specifies Error holds a user-facing error message string. The implementation uses a parameterless data object Error — the message is resolved via stringResource() at render time in the Composable. This was a deliberate design decision (Decision 1 in design.md) to avoid requiring a Context/ResourceProvider in the ViewModel for a single static string. Behaviourally AC-3, AC-4, and AC-10 are all satisfied.

Security Review

PASS — No findings. 0 fix cycles needed. The parameterless Error data object is the correct pattern for preventing information leakage; no exception detail can propagate to the UI.
