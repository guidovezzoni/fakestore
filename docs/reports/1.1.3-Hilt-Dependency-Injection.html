Story Refinement Summary

The story has been significantly expanded from 5 acceptance criteria to 14 detailed, observable-outcome criteria. Comprehensive technical specifications now cover DI architecture, scoping, build configuration, and integration patterns across all modules:

Description & Scope

  • Objective: Integrate Hilt dependency injection framework into the multi-module FakeStore architecture to provide type-safe, automated DI with compile-time graph validation
  • In Scope:
    • Hilt dependency provider modules for :core, :data, and :domain
    • @HiltAndroidApp entry point in :app
    • @AndroidEntryPoint on MainActivity for future ViewModel injection
    • Constructor injection in repositories and use cases
    • Singleton scoping for network and analytics clients
    • Build configuration and annotation processing setup via build-logic convention plugins
    • DI-graph integration test verifying the dependency graph
  • Out of Scope (deferred to future stories):
    • Real ViewModels and feature implementations (no ViewModels exist yet)
    • Database/persistence DI (story 2.1.2)
    • Real analytics SDK wiring

Files & Classes Affected (by intent)

Testing Requirements

  • Unit Tests: Unchanged strategy — test constructor injection via mock/stub parameters, not via DI container
  • DI-Graph Test: At least one test verifying the complete dependency graph assembles, ProductRepository resolves to ProductRepositoryImpl, and debug analytics provider is registered in debug builds
  • Existing Tests: All pre-existing unit tests (1.1.1, 1.1.2) must pass unmodified

Security Considerations

  • Risk Level: Medium
  • Primary Concern: Debug analytics provider (Logcat) must not be registered in release builds — moving registration into the DI graph must preserve this build-variant-level guarantee
  • Other: Dependency supply chain (low), expanded injection entry points (low), generated code correctness (low — verified by compilation and DI-graph test)

Performance Considerations

  • Build time: Medium risk — Hilt annotation processing adds compile-time overhead; should be measured before/after
  • Startup: Low risk — singleton dependencies should be lazily constructed to avoid startup latency
  • Runtime: No impact expected — dependencies are looked up once per consumer lifetime

GDPR & Data Protection

  • Risk Level: Medium
  • Concern: Regression risk — DI migration must preserve the debug-provider release-safety guarantee from story 1.1.2
  • No new personal data introduced — this story only changes how existing objects are constructed

Other Non-Functional Requirements

  • Constructor Injection Convention: Hilt adoption should reinforce constructor injection; field injection only where framework constraints require it (e.g. Activities)
  • Convention-Plugin Alignment: Hilt plugin and annotation processing configured through build-logic convention plugins, not duplicated per module
  • Version Catalogue Discipline: All Hilt dependencies declared in gradle/libs.versions.toml and referenced via libs.*
  • Module Boundary Preservation: :domain must not gain Android/Hilt framework dependencies beyond minimal constructor-injection annotations
  • Kover Readiness: Existing Kover config already excludes Hilt-generated patterns — verify correctness once Hilt is applied

Assumptions

Seven key assumptions documented for review:

  1. No ViewModels exist yet — @HiltViewModel is a standing requirement for future stories (1.2.x+), not testable in this story
  2. KSP vs. kapt decision deferred to propose_change phase
  3. Exact Hilt module file organisation deferred to propose_change phase
  4. Whether NetworkClient and ProductMapper (Kotlin objects) are converted or wrapped is an implementation decision
  5. Hilt version chosen for Kotlin 2.2 and AGP compatibility, pinned in version catalogue
  6. Favourites persistence DI (story 2.1.2) is out of scope
  7. No real analytics SDK is introduced — only the debug provider's registration mechanism changes
