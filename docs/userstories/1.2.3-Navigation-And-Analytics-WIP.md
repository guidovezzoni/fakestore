# Navigation & Product List Analytics

**Epic**: 1 — Product Catalogue
**Feature**: 1.2 — Product List Screen
**Modules**: `:app`, `:core`

## User Story

As a user, I want a bottom navigation bar giving access to Products, Favourites, and Profile so that I can switch screens at any time.

As a product owner, I want a `product_list_viewed` analytics event logged when the screen loads so that catalogue engagement is measurable.

## Description

This story introduces three capabilities to the FakeStore application:

### 1. Bottom Navigation Bar

The application currently renders a single `ProductListScreen` directly inside `MainActivity`. This story adds a persistent bottom navigation bar with three tabs, enabling the user to move between sections of the app. The Products tab hosts the existing `ProductListScreen`. The Favourites and Profile tabs display placeholder screens (empty content with a label), as their full implementations are covered in separate epics (2.x and 3.x).

The navigation bar must remain visible at all times, including during loading and error states. The active tab must be visually distinguished. When the user switches away from a tab and returns, the previous scroll position and content state of that tab must be preserved (i.e. navigating away and back should not trigger a fresh API call or reset the scroll offset).

### 2. Product List Analytics Event

The existing analytics infrastructure (`AnalyticsClient` in `:core`) must be used to log a `product_list_viewed` event each time the user navigates to the Products screen. The event must fire exactly once per screen visit and only after the product list has been successfully loaded (i.e. the `Content` state is reached). It must not fire during the `Loading` or `Error` states, and it must not fire again on recompositions that do not represent a new screen visit.

### 3. Bottom Navigation Tab Tap Events

Each bottom navigation tab tap must log a corresponding analytics event (`tab_products_tapped`, `tab_favourites_tapped`, `tab_profile_tapped`) via `AnalyticsClient`. These events fire on every tap, including tapping the already-selected tab, and carry no parameters.

## Acceptance Criteria

### Bottom Navigation

- [ ] A bottom navigation bar is visible on all screens at all times
- [ ] The bar contains exactly three labelled tabs: **Products**, **Favourites**, **Profile**
- [ ] Each tab displays an appropriate icon alongside its label
- [ ] The currently selected tab is visually highlighted (icon and label)
- [ ] Tapping a tab navigates to its corresponding screen
- [ ] Tapping the already-selected tab has no visible effect (no reload, no scroll reset)
- [ ] Switching between tabs preserves the scroll position and content state of the previously visited tab
- [ ] The Products tab is selected by default when the app launches
- [ ] The Favourites tab displays a centred placeholder text: "Favourites coming soon..."
- [ ] The Profile tab displays a centred placeholder text: "Profile coming soon..."
- [ ] Tab labels are extracted to `strings.xml` for i18n support
- [ ] Navigation is scoped to the `:app` module; feature screens have no dependency on each other

### Product List Analytics

- [ ] A `product_list_viewed` event is logged via `AnalyticsClient` each time the Products screen enters the foreground (each tab navigation to Products counts as one visit)
- [ ] The event is logged only when the screen reaches the successful content state, not during loading or error
- [ ] The event is not logged again on recomposition (e.g. configuration change) within the same screen visit
- [ ] The event carries no parameters (empty `params` map) in this story; future stories may add parameters such as product count
- [ ] The event name follows the existing `snake_case` convention established in `AnalyticsProvider`
- [ ] In debug builds, the event appears in Logcat via `DebugAnalyticsProvider`

### Bottom Navigation Analytics

- [ ] A `tab_products_tapped` event is logged via `AnalyticsClient` each time the user taps the Products tab
- [ ] A `tab_favourites_tapped` event is logged via `AnalyticsClient` each time the user taps the Favourites tab
- [ ] A `tab_profile_tapped` event is logged via `AnalyticsClient` each time the user taps the Profile tab
- [ ] Tab tap events fire on every tap, including tapping the already-selected tab
- [ ] Tab tap events carry no parameters (empty `params` map)
- [ ] In debug builds, tab tap events appear in Logcat via `DebugAnalyticsProvider`

## Data Model

### Analytics Events

| Event name | Trigger | Parameters |
|------------|---------|------------|
| `product_list_viewed` | Products screen reaches Content state (once per visit) | None (empty map) |
| `tab_products_tapped` | User taps the Products tab | None (empty map) |
| `tab_favourites_tapped` | User taps the Favourites tab | None (empty map) |
| `tab_profile_tapped` | User taps the Profile tab | None (empty map) |

No new API endpoints are required. This story uses only the existing Fake Store API endpoint (`GET /products`) already consumed by `ApiService`.

## Unit Testing Strategy

### ProductListViewModel Analytics Tests

Tests should follow the existing pattern in `ProductListViewModelTest.kt` using MockK and `UnconfinedTestDispatcher`. The `createViewModel` factory method should be extended to accept an `AnalyticsClient` parameter (mocked by default). Tests should verify:

- **GIVEN** the Products screen reaches the Content state **WHEN** the tracking intent is dispatched **THEN** `AnalyticsClient.logEvent` is called with `"product_list_viewed"` and an empty params map
- **GIVEN** the Products screen is in Loading state **WHEN** the tracking intent is dispatched **THEN** `AnalyticsClient.logEvent` is not called
- **GIVEN** the Products screen is in Error state **WHEN** the tracking intent is dispatched **THEN** `AnalyticsClient.logEvent` is not called
- **GIVEN** the tracking intent has already been processed once **WHEN** it is dispatched again **THEN** `AnalyticsClient.logEvent` is not called a second time (deduplication within a single ViewModel lifecycle)

### Bottom Navigation Tab Tap Analytics Tests

Tests should verify that each tab tap dispatches the correct analytics event:

- **GIVEN** the user taps the Products tab **WHEN** the tap intent is handled **THEN** `AnalyticsClient.logEvent` is called with `"tab_products_tapped"` and an empty params map
- **GIVEN** the user taps the Favourites tab **WHEN** the tap intent is handled **THEN** `AnalyticsClient.logEvent` is called with `"tab_favourites_tapped"` and an empty params map
- **GIVEN** the user taps the Profile tab **WHEN** the tap intent is handled **THEN** `AnalyticsClient.logEvent` is called with `"tab_profile_tapped"` and an empty params map
- **GIVEN** the user taps the already-selected tab **WHEN** the tap intent is handled **THEN** the corresponding tab tap event is still logged

### Placeholder Screen UI Tests

- **GIVEN** the Favourites screen is displayed **WHEN** the screen renders **THEN** the placeholder text is visible
- **GIVEN** the Profile screen is displayed **WHEN** the screen renders **THEN** the placeholder text is visible

### Navigation UI Tests

- **GIVEN** the app is launched **WHEN** the navigation bar is visible **THEN** the Products tab is selected by default
- **GIVEN** the Favourites tab is tapped **WHEN** the screen renders **THEN** the favourites placeholder is displayed
- **GIVEN** the Profile tab is tapped **WHEN** the screen renders **THEN** the profile placeholder is displayed
- **GIVEN** the user switches from Products to Favourites and back **WHEN** returning to Products **THEN** the previous content state is preserved

## Security Concerns

| Concern | Risk | Mitigation |
|---------|------|------------|
| Analytics event leakage in release builds | LOW | `DebugAnalyticsProvider` is only registered when `BuildConfig.DEBUG` is true (already enforced by `AnalyticsModule`). No production analytics provider is registered yet, so events are silently discarded in release builds. When a production provider is added, ensure it transmits over HTTPS only. |
| Logcat exposure of analytics data | LOW | `DebugAnalyticsProvider` writes to Logcat, which is accessible via ADB on rooted or USB-connected devices. Since `product_list_viewed` contains no parameters and no PII, the exposure risk is negligible. The existing KDoc on `DebugAnalyticsProvider` already warns against registering it in release builds. |
| Navigation deep-link injection | LOW | If type-safe navigation routes are defined as sealed classes/objects, they are not vulnerable to arbitrary string-based deep-link injection. If string-based routes are used, ensure inputs are validated and no sensitive data is passed as route arguments. |

## Performance Concerns

| Concern | Risk | Mitigation |
|---------|------|------------|
| Redundant API calls on tab switch | MEDIUM | Switching tabs must preserve the existing content state. The Products screen should not re-fetch data when the user returns to it. The navigation setup must retain each screen's state across tab switches. |
| Bottom bar recomposition overhead | LOW | The bottom bar should use stable keys for its items to avoid unnecessary recompositions. The number of tabs (3) is fixed and small, so the impact is negligible. |
| Analytics event on every recomposition | MEDIUM | The tracking event must fire only once per screen visit, not on every recomposition. The implementation must guard against duplicate firings caused by configuration changes or recomposition cycles. |

## GDPR and Sensitive Information Concerns

| Concern | Risk | Mitigation |
|---------|------|------------|
| Analytics without user consent | MEDIUM | The `product_list_viewed` event is a behavioural analytics event. Under GDPR, logging user behaviour (even without explicit PII) can constitute processing of personal data when combined with device identifiers. **For this story**: no production analytics provider is registered, so no data leaves the device. **Future requirement**: before a production analytics provider (e.g. Firebase Analytics) is added, a consent mechanism must be implemented. This is out of scope for this story but should be tracked as a prerequisite for any production analytics integration. |
| PII in analytics parameters | LOW | The `product_list_viewed` event carries no parameters. The `AnalyticsProvider` KDoc already prohibits PII in event parameters. No additional mitigation is needed for this story. |
| Placeholder screens and personal data | NONE | The Favourites and Profile screens are placeholders with static text. They do not collect, display, or transmit any personal data. When these screens are implemented in later stories (epics 2.x and 3.x), their own GDPR assessments must be performed. |

## Other Non-Functional Concerns

| Concern | Category | Mitigation |
|---------|----------|------------|
| Accessibility | UX | Tab labels and icons must have appropriate content descriptions. Placeholder screens should be readable by screen readers (TalkBack). |
| Localisation | i18n | All user-facing strings (tab labels, placeholders) must be extracted to `strings.xml`. Both `values/` (EN) and `values-es/` (ES) must be updated simultaneously. |
| Testability | Quality | The navigation composable must be testable with `compose-ui-test-junit4`. The analytics call must be injectable/mockable via the existing `AnalyticsClient` class. |
| Back button behaviour | UX | Pressing the system back button from a non-Products tab should navigate back to the Products tab (as the start destination). Pressing back from the Products tab should exit the app. This follows standard Android bottom-navigation conventions. |
| Kover coverage threshold | Quality | New code must maintain the 95% minimum coverage bound. The Kover exclusion for `*.ui.screens.*` already covers composable screen files; ViewModel logic is tested via unit tests. |
| Detekt compliance | Quality | All new code must pass `./gradlew detektDebug` with zero violations. New composable functions must follow PascalCase naming (covered by `FunctionNaming: ignoreAnnotated: ['Composable']`). |

## Assumptions

1. The Compose Navigation library (`androidx.navigation:navigation-compose`) is the intended navigation solution, as `hilt-navigation-compose` is already present in the version catalog for ViewModel injection.
2. The Favourites and Profile screens are intentionally empty placeholders in this story. Their full implementation is covered by epics 2.x and 3.x respectively.
3. No production analytics provider is in scope. The `product_list_viewed` event will only be observable in debug builds via Logcat.
4. The `product_list_viewed` event needs no parameters in this story. Adding parameters (e.g. product count, load duration) is deferred to a future analytics enhancement story.
5. The analytics tracking should be counted as "once per screen visit" where a visit is defined as each time the user navigates to the Products tab (including the initial app launch). Re-entering the tab after switching away counts as a new visit.

### Technical Notes

- Routes defined as a sealed class / type-safe object in `:app`
- Feature screens do not depend on each other — navigation is orchestrated only in `:app`
