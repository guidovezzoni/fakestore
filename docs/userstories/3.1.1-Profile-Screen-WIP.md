# Profile Screen

**Epic**: 3 -- User Profile
**Feature**: 3.1 -- Profile Screen
**Modules**: `:app`, `:core`, `:domain`, `:data`

## User Story

As a user, I want a Profile screen that displays my name, email, and live favourite count -- with loading and error states -- so that I can see my account information at a glance.

As a product owner, I want a `profile_screen_viewed` analytics event logged when the Profile screen loads.

## Description

The Profile screen replaces the current placeholder with a fully functional screen that fetches user profile data from the Fake Store API and combines it with a live favourite count sourced from the local favourites database. The screen follows the same MVI pattern, loading/error state conventions, and analytics approach already established by the Products and Favourites screens.

The user ID is hardcoded to `8` for this demo application. No authentication or user-selection flow is in scope.

### What is displayed

- **Full name**: derived from the API's `firstname` and `lastname` fields (combined into a single display string, e.g. "William Hopkins")
- **Email address**: from the API's `email` field (e.g. "william@gmail.com")
- **Live favourite count**: the number of currently favourited products, derived from the existing local favourites data source (same data that drives the Favourites screen)

### What is NOT displayed or stored

- **Password**: the API returns a `password` field in plaintext. This field MUST be excluded from all DTOs, domain models, and any layer of the application. It must never be deserialised, stored, logged, or transmitted further. See Security and GDPR sections below.
- **Phone number**: not required for this story. Exclude from DTOs and domain models.
- **Address / geolocation**: not required for this story. Exclude from DTOs and domain models.
- **Username**: included in the domain model for potential future use, but not displayed on the Profile screen in this story.
- **`__v`**: internal API versioning field. Exclude from all models.

## API Endpoint

### `GET https://fakestoreapi.com/users/8`

**Response shape** (fields relevant to this story are marked with *):

```json
{
  "id": 8,                          
  "email": "william@gmail.com",     // * displayed
  "username": "hopkins",            // * stored in domain model, not displayed
  "password": "William56$hj",       // EXCLUDED - never deserialise
  "name": {                         // * nested object
    "firstname": "william",         // * used to build display name
    "lastname": "hopkins"           // * used to build display name
  },
  "phone": "1-478-001-0890",        // EXCLUDED
  "address": { ... },               // EXCLUDED (contains geolocation PII)
  "__v": 0                          // EXCLUDED
}
```

**Note**: The `name` field is a nested object with `firstname` and `lastname`. Per project guidelines ("preserve meaningful domain concepts as value objects"), the name should be modelled as a separate value object in the domain layer (e.g. `Name` with `firstName` and `lastName` fields), rather than flattening into the parent `UserProfile`.

## Acceptance Criteria

### User Profile Data
- [ ] `GET https://fakestoreapi.com/users/8` is called when the Profile screen loads
- [ ] The response is mapped to a `UserProfile` domain model containing: name (as a `Name` value object with `firstName` and `lastName`), email, and username
- [ ] The `password`, `phone`, `address`, and `__v` fields from the API response are never deserialised or stored
- [ ] The user's full name (firstname + lastname, properly capitalised) is displayed on the Profile screen
- [ ] The user's email address is displayed on the Profile screen

### Favourite Count
- [ ] The number of favourited products is shown on the Profile screen
- [ ] The count updates reactively -- no manual refresh required after toggling a product on another screen
- [ ] The count is derived from `GetFavouriteIdsUseCase` (the existing use case), not from a separate API call

### Loading & Error States
- [ ] A loading indicator is shown while the user profile is being fetched
- [ ] An error message with a "Retry" button is shown if the API call fails
- [ ] The favourite count continues to update reactively even while a profile reload is in flight
- [ ] Loading and error states follow the same visual pattern used on the Products screen (centred indicator, centred error text with retry button)

### Analytics
- [ ] `profile_screen_viewed` is logged once each time the Profile screen enters composition
- [ ] The event is logged regardless of whether the profile data has loaded yet
- [ ] The event follows the same pattern as `product_list_viewed` on the Products screen

### Accessibility
- [ ] All displayed text elements have appropriate semantics for screen readers
- [ ] The retry button is focusable and operable via accessibility services

### Internationalisation
- [ ] All user-facing strings (screen title, error message, retry button label, favourite count label) are extracted to `strings.xml`
- [ ] The corresponding Spanish translations are added to `values-es/strings.xml`
- [ ] The error message and retry button label should reuse existing string resources where the text is identical (e.g. `product_list_error_message`, `product_list_retry_button`)

## Files to Create or Modify

### `:domain` module -- domain models, repository interface, use case
- **New domain model**: `UserProfile` -- represents the user's profile data (id, name, email, username)
- **New domain value object**: `Name` -- represents the user's name (firstName, lastName)
- **New repository interface**: `UserRepository` -- exposes a method to fetch a user profile by ID, returning domain types only
- **New use case**: `GetUserProfileUseCase` -- wraps the repository call, exposes `Flow<Result<UserProfile>>` following the same pattern as `GetProductsUseCase`

### `:data` module -- DTOs, mapper, API endpoint, repository implementation
- **New DTO**: `UserDto` -- `@Serializable` data class matching the API response shape for the fields we consume (id, email, username, name). Must NOT include `password`, `phone`, `address`, or `__v`
- **New DTO**: `NameDto` -- `@Serializable` data class for the nested name object (firstname, lastname)
- **Modify API service**: add a `GET users/{id}` endpoint method
- **New mapper**: `UserMapper` -- maps `UserDto` to `UserProfile` domain model (lives in `:data/mapper/`)
- **New repository implementation**: `UserRepositoryImpl` -- implements `UserRepository`, uses the API service and mapper

- **Modify screen**: replace the `ProfileScreen` placeholder composable with full implementation displaying profile data with loading/error states
- **Modify DI module**: register `UserRepository`, `UserRepositoryImpl`, and `GetUserProfileUseCase` for injection
- **Modify strings**: add new string resources for the Profile screen (screen title, favourite count label, error/retry if not reusing existing ones)
- **Modify Spanish strings**: add corresponding translations

### `:app` module -- tests
- **New unit test**: `ProfileViewModelTest` -- tests all intents, state transitions, error handling, analytics logging
- **New unit test**: `GetUserProfileUseCaseTest` -- tests success and failure flows
- **New unit test**: `UserRepositoryImplTest` -- tests mapping from DTO to domain model

## Unit Testing Approach

Following existing project conventions (JUnit 4, MockK, `runTest`, `UnconfinedTestDispatcher`):

### ProfileViewModelTest
- **GIVEN** fresh ViewModel **WHEN** `LoadProfile` intent is dispatched **THEN** state is `Loading` then `Content` with correct profile fields and favourite count
- **GIVEN** fresh ViewModel **WHEN** API call fails **THEN** state transitions to `Error`
- **GIVEN** `Error` state **WHEN** `RetryClicked` intent is dispatched **THEN** state transitions to `Loading` and retries the API call
- **GIVEN** `Content` state **WHEN** favourites change on another screen **THEN** favourite count updates reactively without re-fetching the profile
- **GIVEN** fresh ViewModel **WHEN** `TrackScreenViewed` intent is dispatched **THEN** `profile_screen_viewed` analytics event is logged exactly once
- **GIVEN** profile loading in flight **WHEN** `TrackScreenViewed` is dispatched **THEN** analytics event is still logged (does not wait for profile data)

### GetUserProfileUseCaseTest
- **GIVEN** repository returns a valid `UserProfile` **WHEN** use case is invoked **THEN** emits `Result.success` with the profile
- **GIVEN** repository throws an exception **WHEN** use case is invoked **THEN** emits `Result.failure` with the exception

### UserRepositoryImplTest
- **GIVEN** API returns a valid `UserDto` **WHEN** `getUserProfile` is called **THEN** returns a correctly mapped `UserProfile` domain model

### UserMapperTest
- **GIVEN** a `UserDto` with lowercase name fields **WHEN** mapped **THEN** the domain `Name` fields preserve the original casing (capitalisation is a presentation concern, not a mapping concern)
- **GIVEN** a `UserDto` with all fields populated **WHEN** mapped **THEN** all domain model fields are correctly set

### ProfileScreenTest (Compose UI test)
- **GIVEN** `Loading` state **WHEN** screen renders **THEN** loading indicator is visible
- **GIVEN** `Content` state with name, email, and count **WHEN** screen renders **THEN** all three values are displayed
- **GIVEN** `Error` state **WHEN** screen renders **THEN** error message and retry button are visible

## Security Concerns and Mitigations

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **API returns plaintext passwords** | **CRITICAL** | The `password` field MUST be excluded from all DTO classes. By not declaring the field in the `@Serializable` DTO, kotlinx-serialization will ignore it during deserialisation (with `ignoreUnknownKeys = true` on the JSON configuration). The password must never enter application memory. Verify this is enforced via code review and a dedicated unit test asserting the DTO has no `password` property. |
| **PII transmitted over the network** | HIGH | The API is served over HTTPS, which provides transport-layer encryption. However, the response contains PII (email, name) that is held in memory. Ensure no PII is included in analytics events, log statements, or crash reports. |
| **Hardcoded user ID** | LOW | The user ID `8` is hardcoded. This is acceptable for a demo app. If authentication were added in future, the ID would come from an auth token, not a hardcoded value. Document this as a known simplification. |
| **No authentication** | LOW | The Fake Store API does not require authentication for `GET /users/{id}`. In a production app, user profile endpoints would be authenticated. Not in scope for this demo. |

## Performance Concerns and Mitigations

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Network call on every screen visit** | MEDIUM | The profile data is unlikely to change frequently. Consider whether caching (in-memory or on-disk) is warranted. For this demo app with a static API, an in-memory cache in the repository or ViewModel (via `rawProfile` state, similar to the existing `rawProducts` pattern) is sufficient. The profile should not be re-fetched if already loaded and the user navigates away and back. |
| **Combining two data sources** | LOW | The ViewModel combines a network-sourced profile flow with a local-database-sourced favourites flow. Both are lightweight. The favourite count flow is already proven performant in the existing Favourites screen. No additional mitigation needed. |
| **Unnecessary recompositions** | LOW | The UiState is an immutable sealed interface. Compose's structural equality checks will prevent recomposition when the state has not changed. Follow the existing pattern. |

## GDPR and Sensitive Information Concerns

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Password exposure from API** | **CRITICAL** | Even though this is a fake/demo API, the pattern must be correct: never deserialise or store password data. The DTO must not contain a `password` field. A unit test should verify that `UserDto` does not have a `password` property via reflection, as a safeguard against accidental addition. |
| **PII displayed on screen (name, email)** | HIGH | Name and email are personal data under GDPR. For this demo app, no consent flow is required (the data is fake). However, the implementation must ensure: (1) PII is not logged at any level (AnalyticsClient params, Logcat, crash reports); (2) PII is not included in analytics event parameters; (3) PII is not persisted locally (it is fetched on demand and held only in memory). |
| **Geolocation data in API response** | HIGH | The API returns latitude/longitude coordinates in the `address.geolocation` field. This is sensitive location data under GDPR. Mitigation: exclude `address` entirely from the DTO so it is never deserialised. |
| **Data minimisation principle** | MEDIUM | GDPR Article 5(1)(c) requires that only data adequate and relevant to the purpose is processed. The DTO should declare only the fields needed for display (id, name, email, username), ensuring compliance with data minimisation by design. |
| **No local persistence of profile data** | LOW | Profile data is fetched on demand and held in ViewModel memory only. It is cleared when the ViewModel is destroyed. No Room/SharedPreferences storage of user PII is introduced. This is compliant with the storage limitation principle. |

## Other Non-Functional Requirements

| Concern | Category | Mitigation |
|---------|----------|------------|
| **Offline behaviour** | Reliability | If the device is offline, the API call will fail and the error state with retry button will be shown. The favourite count (sourced from local Room database) should still display if the profile has been previously loaded and is cached in the ViewModel. |
| **Screen rotation / configuration change** | Reliability | The ViewModel survives configuration changes (standard Hilt ViewModel behaviour). The loaded profile data should not be re-fetched on rotation. |
| **Name capitalisation** | UX | The API returns lowercase names (e.g. "william", "hopkins"). The display name should be properly capitalised (e.g. "William Hopkins"). This capitalisation is a presentation concern and should be handled when building the UiState, not in the domain model or mapper. |
| **Empty or missing API fields** | Robustness | The DTO should handle nullable or missing optional fields gracefully. The `username` field should have a sensible default if absent. |
| **Consistent error UX** | UX | The error state should reuse the same error message and retry button pattern as the Products screen for a consistent user experience. Reuse existing string resources where the message is identical. |
| **Test tags for Compose UI tests** | Testability | Key UI elements (loading indicator, error container, retry button, name text, email text, favourite count) should have test tags for Compose UI testing, following the existing pattern (e.g. `PRODUCT_LIST_LOADING_INDICATOR_TEST_TAG`). |

## Assumptions

1. **User ID is hardcoded to 8** -- there is no authentication or user-selection mechanism. This is a demo app simplification.
2. **`ignoreUnknownKeys` is enabled** on the JSON configuration -- so fields not declared in the DTO (password, phone, address, __v) will be silently ignored during deserialisation. If not currently enabled, it must be configured.
3. **The existing `GetFavouriteIdsUseCase`** is the correct use case for deriving the favourite count (the original story referenced `GetFavouritesUseCase` which does not exist in the codebase).
4. **Name capitalisation** is a presentation concern handled in the ViewModel/UiState mapping, not in the domain layer.
5. **No new navigation changes** are needed -- the `AppDestination.Profile` route already exists and is wired into the `NavHost` in `MainScreen`.
6. **Shared loading/error composables**: the original story mentions shared loading/error composables from `:ui`. Currently, each screen has its own private loading/error composables (e.g. `ProductListLoadingContent`, `FavouritesLoadingContent`). Whether to extract shared composables or duplicate the pattern is an implementation decision for the propose phase.
