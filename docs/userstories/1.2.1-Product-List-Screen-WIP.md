# Product List Screen

**Epic**: 1 -- Product Catalogue
**Feature**: 1.2 -- Product List Screen
**Story ID**: 1.2.1
**Role**: User
**Status**: Refined
**Modules affected**: `:app`

## User Story

As a user, I want a scrollable list of products showing each product's image, title, and price so that I can browse the catalogue.

## Description

This story delivers the first user-facing screen of the application: a vertically scrollable list of product cards. It replaces the current placeholder "Hello Android" screen in `MainActivity` with a product list that fetches data from the existing `GetProductsUseCase` (delivered in story 1.1.1) and displays it.

The scope covers:

- Creating a product list screen composable that displays products in a vertical scrollable list
- Creating a product card composable showing product image, title, and price
- Creating a ViewModel following the MVI pattern to manage the screen state
- Creating MVI artefacts: UiState, UiIntent, UiEffect
- Loading product images asynchronously from their URLs
- Wiring the screen into `MainActivity` as the initial/default screen
- Adding an image loading library dependency to the version catalogue
- Adding user-facing strings to `strings.xml`

This story delivers the **content state only** (products displayed successfully). Loading, error, and empty states are covered in story 1.2.2. Bottom navigation is covered in story 1.2.3. Favourite toggle functionality is covered in story 2.1.1.

### Scope Boundaries

| Vertical scrollable list of cards | Loading / error / empty states (1.2.2) |

## API Endpoint

This story consumes the existing data pipeline established in story 1.1.1. No new API integration is required.

- **Use case**: `GetProductsUseCase` (in `:domain`)
- **Signature**: `operator fun invoke(): Flow<Result<List<Product>>>`
- **Underlying endpoint**: `GET https://fakestoreapi.com/products`
- **Response**: JSON array of 20 product objects (see story 1.1.1 for full schema)

## Data Displayed

The following fields from the `Product` domain model are displayed on each product card:

| Display Element | Source Field | Type | Display Behaviour |
|-----------------|-------------|------|-------------------|
| Product image | `Product.imageUrl` | `String` (URL) | Loaded asynchronously; placeholder shown while loading; graceful fallback on failure |
| Product title | `Product.title` | `String` | Displayed in full; long titles may wrap to multiple lines |
| Product price | `Product.price` | `Double` | Formatted as currency (e.g. "$109.95"); formatting logic lives in the ViewModel, not the composable |

The following `Product` fields are **not displayed** in this story but are available in the domain model for future use:

| Field | Deferred To |
|-------|-------------|
| `description` | Product detail screen (future) |
| `category` | Category filtering (future) |
| `rating` (score, count) | Product detail or list enhancement (future) |

## MVI Contract

### UiState

A single immutable data class representing the product list screen state. For this story, only the content state is required (loading/error/empty states are added in 1.2.2).

| Field | Type | Default | Purpose |
|-------|------|---------|---------|
| `products` | `List<ProductListItem>` | `emptyList()` | The list of display-ready product items |

Where `ProductListItem` is a display-ready model holding pre-formatted values (e.g. formatted price string, image URL, title). The ViewModel maps from `Product` domain model to this display model so that composables contain no formatting logic.

### UiIntent

Sealed class of user actions the screen can trigger.

| Intent | Trigger | Purpose |
|--------|---------|---------|
| `LoadProducts` | Screen first composition | Requests initial product data load |

> Note: Story 1.2.2 will add a `RetryClicked` intent. Story 2.1.1 will add `ToggleFavourite(productId)`.

### UiEffect

Sealed class for one-shot side effects. For this story, no effects are required, but the structure should be established for future stories (e.g. `ShowError` in 1.2.2).

### ViewModel

- Exposes `uiState: StateFlow<ProductListUiState>` and `uiEffect: SharedFlow<ProductListUiEffect>`
- Receives intents via `fun onIntent(intent: ProductListUiIntent)`
- On `LoadProducts`: invokes `GetProductsUseCase`, collects the result, and updates `uiState` with the product list
- Price formatting is computed in the ViewModel and exposed as a display-ready value (the composable does not perform formatting)

## Testing

### Unit Tests

| Class Under Test | What to Test |
|------------------|--------------|
| `ProductListViewModel` | `LoadProducts` intent triggers use case and populates `uiState.products`; successful result updates state with the product list; price formatting produces correct display strings (e.g. `109.95` becomes `"$109.95"`); state is not reset on duplicate `LoadProducts` intents |

**Test approach**:

- Mock `GetProductsUseCase` to return controlled `Flow<Result<List<Product>>>` values

- Use JUnit 4 and MockK

- Follow `GIVEN / WHEN / THEN` naming convention
- Use a `createViewModel(...)` factory method in tests for varied setup
- Target 95%+ coverage

## Security Considerations

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Loading images from external URLs** | Medium | Product images are loaded from `fakestoreapi.com` HTTPS URLs. The image loading library should enforce HTTPS-only. On API 24+ (the project's `minSdk`), Android's default network security config blocks cleartext. Verify no cleartext HTTP image URLs can be loaded. |
| **Image loading library permissions** | Low | The image loading library requires `INTERNET` permission (already granted for API calls). Verify the library does not request unnecessary permissions. |
| **Malicious image content** | Low | Images are rendered from a known test API. In a production context, consider content validation or a CDN proxy. For this demo, the risk is acceptable. |
| **Denial of service via large images** | Low | A malformed or excessively large image could consume excessive memory. The image loading library should enforce size limits and downsampling. This is typically default behaviour in modern image loaders. |

## Performance Considerations

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Image loading and memory** | Medium | Images should be loaded lazily (only when visible), cached in memory and on disk, and downsampled to the display size. The image loading library handles this, but the composable should specify a fixed size or `contentScale` to enable efficient downsampling. |
| **List scrolling performance** | Medium | The list must use a lazy layout (not a `Column` with `verticalScroll`) to avoid composing all 20 items at once. Each card should have a stable key (e.g. `product.id`) to avoid unnecessary recompositions during scrolling. |
| **Recomposition overhead** | Low | The product list should use stable, immutable data classes for list items. Avoid creating new lambda instances on each recomposition where possible. |
| **Initial load time** | Low | 20 products is a small dataset. The API call and JSON parsing are negligible (see story 1.1.1 performance notes). Image loading is progressive, so the list renders immediately with placeholders. |

## GDPR and Sensitive Information

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Personal data displayed** | None | The product list displays only product catalogue data (images, titles, prices). No PII is shown or processed. |
| **Image caching on device** | Low | The image loading library caches images on disk. These are product images (not personal data) and do not require GDPR consent or deletion mechanisms. If the app later caches user-generated content, this should be revisited. |
| **User behaviour tracking** | None | This story does not include analytics. User interaction tracking is covered in story 1.2.4. |

## Other Non-Functional Requirements

| Concern | Category | Mitigation |
|---------|----------|------------|
| **Accessibility** | Usability | Product images must have content descriptions (e.g. the product title). Price and title text must meet minimum contrast ratios per WCAG AA. |
| **Internationalisation** | Usability | User-facing strings (screen title, content descriptions) must be in `strings.xml`. Price formatting should use locale-aware formatting if feasible. The base language is UK English per project guidelines. |
| **Screen rotation / configuration changes** | Reliability | The product list state must survive configuration changes (screen rotation). The ViewModel's `StateFlow` handles this naturally. Scroll position should be preserved across configuration changes via the lazy list's saved state. |
| **Dark mode** | Usability | The screen must render correctly in both light and dark themes using the existing `FakeStoreTheme` and Material 3 colour tokens. Product card backgrounds and text must have sufficient contrast in both modes. |
| **Edge-to-edge display** | Usability | The screen must respect system bar insets (status bar, navigation bar) using the existing `Scaffold` and edge-to-edge setup in `MainActivity`. |
| **Memory pressure** | Reliability | When the app is backgrounded and the system reclaims memory, the screen should recover gracefully on return (ViewModel survives process death via Hilt; data is re-fetched if needed). |
| **Testability** | Maintainability | All dependencies injected via constructor. Composables are stateless and receive data via parameters. No business logic in composables. |

## Assumptions

1. The `GetProductsUseCase` and the full data pipeline from story 1.1.1 are complete and functional.
2. Hilt dependency injection from story 1.1.3 is in place, providing `GetProductsUseCase` to the ViewModel.
3. This story delivers only the **content state** (products displayed). Loading, error, and empty states are deferred to story 1.2.2, which will extend the `UiState` with additional variants.
4. The favourite toggle icon is not included in the product card layout; it will be added in story 2.1.1 when the toggle functionality is delivered.
5. Bottom navigation is not included; the product list is shown as the sole screen. Story 1.2.3 will add the navigation bar.
6. The product list screen is the initial screen shown when the app launches, replacing the current placeholder.
7. The specific image loading library will be chosen during the implementation phase. The acceptance criteria specify the required behaviour (async loading, placeholder, fallback) without prescribing a specific library.
8. Price is displayed in USD format (e.g. "$109.95") for the current dataset. Full locale-aware currency formatting is a future enhancement if multi-currency support is needed.
9. No new Gradle module (e.g. `:ui`) is created in this story. The decision on whether to introduce a shared UI module for reusable Compose components is deferred to the implementation phase, where it can be evaluated against the current codebase structure. All new files live in `:app` for now.
