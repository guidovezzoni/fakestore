# Favourite Toggle & Persistence

**Epic**: 2 -- Favourites Management
**Feature**: 2.1 -- Favourite Toggle & Persistence
**Story**: 2.1.1 -- Favourite Toggle
**Modules**: `:app`, `:domain`, `:data`, `:core`

---

## Description

Users can mark any product as a favourite by tapping a toggle icon on its product card. The toggle must provide immediate visual feedback (optimistic update), persist the state locally so it survives app restarts, and be consistent across all screens that display products (Products list, Favourites list). Each toggle action must emit an analytics event with the product ID.

Favourites are stored **locally only** using Room. There is no remote API endpoint for favourites -- the existing Fake Store API (`/products`) is read-only and does not support favourites. The Room database will store only the product IDs of favourited items.

---

## User Stories

**As a user**, I want to tap a toggle icon on a product card to add or remove it from favourites so that the action is immediate, visible, and persisted across app restarts.

**As a product owner**, I want `favourite_added` and `favourite_removed` analytics events (with product ID) logged on each toggle so that favouriting behaviour is measurable.

---

## Acceptance Criteria

### Favourite icon display
- [ ] Each product card on the Products screen shows a heart icon
- [ ] The icon is **filled** when the product is a favourite and **outlined** when it is not
- [ ] The icon has an accessible content description (e.g. "Add to favourites" / "Remove from favourites") that reflects the current state

### Toggle behaviour
- [ ] Tapping the icon toggles the favourite state immediately in the UI (optimistic update)
- [ ] If the underlying database write fails, the UI reverts to the previous state and the user is notified via a snackbar

### Persistence
- [ ] Favourite product IDs are stored in a local Room database table
- [ ] The stored data is the **product ID only** (integer) -- no other product fields are persisted in the favourites table
- [ ] On app restart, the persisted IDs are loaded and the favourite icons reflect the saved state
- [ ] Adding a favourite inserts a row; removing a favourite deletes the corresponding row

### Favourites screen
- [ ] The Favourites screen (currently a placeholder) displays only favourited products
- [ ] When no products are favourited, the Favourites screen shows an empty state message
- [ ] Removing a favourite from the Favourites screen removes the product from the displayed list
- [ ] The favourite icon state is consistent between the Products screen and the Favourites screen (toggling on one screen is reflected on the other)

### Analytics
- [ ] `favourite_added` is logged with param `product_id` (Int) when a product is added to favourites
- [ ] `favourite_removed` is logged with param `product_id` (Int) when a product is removed from favourites
- [ ] No analytics event is logged if the toggle operation fails (e.g. database error)
- [ ] Analytics events are dispatched after successful persistence, not on tap

### Domain layer
- [ ] A `ToggleFavouriteUseCase` in `:domain` encapsulates the toggle logic
- [ ] A `FavouritesRepository` interface in `:domain` defines the contract for favourite operations
- [ ] The domain layer has no dependency on Room, Android, or data-layer types

### Strings / i18n
- [ ] All new user-facing strings are extracted to `strings.xml`
- [ ] Existing locale directories (if any) are updated with translated strings

## Data Model

### Room Entity (`:data` module)

| Field | Type | Notes |
|-------|------|-------|
| `productId` | `Int` | Primary key. Corresponds to `Product.id` from the domain model. |

No additional columns are needed. The entity stores only the product ID, keeping the table lightweight. Full product details are already available from the API product list.

### Domain Model Changes

No new domain model class is required. The favourite state is a boolean flag derived by checking whether a product's ID exists in the set of favourite IDs. This flag is surfaced through the UI state layer.

### UI State Changes

**`ProductListItem`** -- add:

| Field | Type | Default | Notes |
|-------|------|---------|-------|
| `isFavourite` | `Boolean` | `false` | Whether this product is currently favourited |

## Endpoints / Data Sources

### Remote API
No changes. The existing `ApiService.getProducts()` endpoint remains the sole source of product data. Favourites are not synced remotely.

### Local Database (Room)
- **Table**: `favourite_entity` (or similar, determined at implementation time)
- **Operations**:
  - **Insert**: add a product ID to favourites
  - **Delete**: remove a product ID from favourites
  - **Query all**: return all favourite product IDs as a reactive stream (`Flow<List<Int>>`)
  - **Query single** (optional): check if a specific product ID is favourited

## Security Concerns and Mitigations

| Concern | Risk | Mitigation |
|---------|------|------------|
| Room database stored in plain text on device | Low -- favourite product IDs are non-sensitive integers | No encryption needed. The data is a list of integer IDs with no PII, financial data, or authentication tokens. |
| SQL injection via product ID | Negligible -- Room uses parameterised queries by default | Use Room's DAO annotations (`@Insert`, `@Delete`, `@Query`) which parameterise inputs automatically. Do not construct raw SQL with string interpolation. |
| Analytics event data leakage | Low -- only product ID (integer) is sent | Ensure analytics params contain only `product_id` (Int). Never include user identifiers, device info, or other fields not explicitly listed. This aligns with the existing `AnalyticsProvider` contract which prohibits PII. |
| Exported database via backup | Low | Android's default backup rules may include the database. If the app later stores sensitive data, consider adding `android:allowBackup="false"` or defining backup rules. For integer product IDs, this is acceptable. |

## Performance Concerns and Mitigations

| Concern | Risk | Mitigation |
|---------|------|------------|
| Combining product list with favourite IDs on every emission | Low -- the Fake Store API returns ~20 products | The combination operation (set lookup per product) is O(n) with a small n. If product count grows significantly, consider profiling. |
| Room reactive query triggering recomposition | Low -- Room emits only when the table changes | Room's `Flow`-based queries emit only on actual data changes. Combined with `StateFlow` deduplication, unnecessary recompositions are avoided. |
| Database write on main thread | Medium if not handled | All Room operations must run on a background dispatcher. Room enforces this by default (throws on main-thread access). Use coroutines with appropriate dispatchers. |
| Favourites screen loading all products from API just to display favourites | Medium | The Favourites screen needs the full product list (from the API) filtered by favourite IDs. Consider whether the existing `GetProductsUseCase` result can be shared/cached rather than fetched independently for each screen. |

## GDPR and Sensitive Information

| Concern | Assessment | Mitigation |
|---------|------------|------------|
| Personal data in favourites | **No PII is stored.** The favourites table contains only integer product IDs. No user account, name, email, or behavioural profile is persisted. | No GDPR data subject rights (access, erasure, portability) apply to this data in isolation. |
| Behavioural profiling via analytics | **Low risk.** Analytics events contain only `product_id`. Without a user identifier, individual preferences cannot be reconstructed from the analytics backend. | If a user identifier is added to analytics in the future, a privacy impact assessment should be conducted. For now, events are anonymous. |
| Data retention | Favourites persist indefinitely on-device until the user uninstalls the app or clears app data. | This is standard for local preferences. No server-side retention policy is needed since data is not synced. If the app adds user accounts or cloud sync in the future, a data retention and deletion policy must be defined. |
| Right to erasure | Uninstalling the app or clearing app data removes the Room database. | Sufficient for local-only data. Document this in a privacy notice if one exists. |
