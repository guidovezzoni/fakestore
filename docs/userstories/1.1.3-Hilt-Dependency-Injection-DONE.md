# Hilt Dependency Injection

**Epic**: 1 — Product Catalogue
**Feature**: 1.1 — Data Layer & Analytics Setup
**Story ID**: 1.1.3
**Role**: Developer
**Status**: Refined
**Modules**: `:app`, `:core`, `:domain`, `:data`

## User Story

As a developer, I want Hilt configured end-to-end so that the network client, analytics client, repositories, and use cases are provided through a managed dependency graph instead of being constructed manually — and so that future ViewModels can be injected without additional wiring.

## Description

This story introduces Hilt as the project's dependency injection framework, replacing ad-hoc manual construction of dependencies with a managed object graph. It establishes the DI infrastructure across all four modules (`:app`, `:core`, `:domain`, `:data`) so that every dependency created in stories 1.1.1 (data layer) and 1.1.2 (analytics) becomes injectable, and so that future feature stories (1.2.x onward) can inject `ViewModel`s without introducing their own wiring conventions.

**Current state**: the codebase has no manual DI container or factory layer at all — it is greenfield. `NetworkClient` in `:core` is a Kotlin `object` singleton; `ProductRepositoryImpl`, `GetProductsUseCase`, and the analytics classes are plain classes with constructor parameters that nothing currently wires together (no `ViewModel`s exist yet to consume them, and `MainActivity` does not reference any of them). This story is therefore establishing the DI foundation proactively, ahead of the UI stories that will consume it.

The scope covers:
- Enabling Hilt at the application level (the `Application` class becomes the root of the dependency graph)
- Making the configured network client (Retrofit/OkHttp) available through injection, as a singleton, instead of a manually-referenced `object`
- Making the `AnalyticsClient` available through injection, as a singleton, with provider registration (e.g. the debug Logcat provider from 1.1.2) driven by build type rather than a manual call site
- Making `ProductRepository` resolve to its `ProductRepositoryImpl` implementation automatically through injection, without any module depending on the concrete class
- Making `GetProductsUseCase` and `ApiService` injectable
- Preparing `MainActivity` (and any future Activities/Fragments) to act as an injection entry point, so that when 1.2.x introduces `ViewModel`s, they can be annotated for injection with no further infrastructure work
- Unit test strategy for DI-provided components, including whether/where Hilt's test rules are needed

This story does **not** include:
- Creating any `ViewModel` — none exist in the codebase yet; they will be introduced by 1.2.x and later stories and are expected to use the infrastructure this story provides
- Wiring a real analytics SDK (Firebase, Mixpanel, etc.) — out of scope per 1.1.2
- Database/persistence DI (e.g. Room for favourites, story 2.1.2) — this story covers only dependencies that exist today
- Consent management or any change to analytics behaviour — this story only changes *how* existing objects are constructed, not what they do

### Relationship to the Original Acceptance Criteria

The original story's acceptance criterion "`@HiltViewModel` used on all ViewModels" cannot be satisfied literally today because no `ViewModel` exists in the codebase. This refinement reframes that criterion as a **standing requirement for future work**: any `ViewModel` added from this point forward must be injectable via Hilt, and the infrastructure delivered by this story must make that possible without rework. See the Definition of Done for how this is verified within this story's own scope.

## Acceptance Criteria

- [ ] The application starts successfully with Hilt's dependency graph initialised at process start
- [ ] The configured network client (Retrofit/OkHttp instance, base URL `https://fakestoreapi.com`) is obtained via injection wherever it is needed, with exactly one instance per application process (singleton scope)
- [ ] `AnalyticsClient` is obtained via injection, with exactly one instance per application process (singleton scope)
- [ ] The debug analytics provider (Logcat, from 1.1.2) is automatically registered with `AnalyticsClient` in debug builds through the dependency graph — no manual `register()` call is required at any call site
- [ ] The debug analytics provider is **not** registered in release builds — this must be verifiable by build variant, not by a runtime flag that could be misconfigured
- [ ] `ProductRepository` consumers receive a `ProductRepositoryImpl` instance via injection, with no consumer referencing the concrete implementation class directly
- [ ] `GetProductsUseCase` and `ApiService` are obtained via injection rather than manual construction
- [ ] `MainActivity` is set up as a Hilt injection entry point, so that a `ViewModel` added in a future story can be injected into it without further DI infrastructure changes
- [ ] No class in `:core`, `:domain`, or `:data` that participates in the dependency graph is manually instantiated from `:app` (i.e. no `NetworkClient.retrofit`-style direct object access remains for graph-managed types)
- [ ] All new/modified classes retain or gain unit test coverage equivalent to their pre-Hilt state (existing tests for `AnalyticsClient`, `GetProductsUseCase`, `ProductRepositoryImpl`, etc. continue to pass without depending on the Hilt graph)
- [ ] `./gradlew assembleDebug` succeeds with Hilt annotation processing enabled
- [ ] `./gradlew test` passes
- [ ] `./gradlew detektDebug` passes with no new violations
- [ ] `./gradlew koverVerify` passes (95%+ coverage on new/modified code, excluding Hilt-generated code)

## Files/Classes Affected (by intent)

| Area | Module | Intent |
|------|--------|--------|
| Application class | `:app` | Establish the root of the Hilt dependency graph at process start |
| `MainActivity` | `:app` | Become a Hilt injection entry point so future screens can receive injected `ViewModel`s |
| Network client provisioning | `:core` | Make the configured Retrofit/OkHttp instance available through injection instead of a manually-referenced `object` singleton |
| Analytics client provisioning | `:core` | Make `AnalyticsClient` available through injection; make provider registration (debug vs. release) build-type-driven rather than a manual call |
| `ApiService` provisioning | `:data` | Make the API service available through injection |
| `ProductRepository` → `ProductRepositoryImpl` resolution | `:data` / `:domain` | Ensure consumers depending on the `:domain` interface receive the `:data` implementation automatically, without referencing the concrete class |
| `GetProductsUseCase` | `:domain` | Make the use case injectable (constructor-injectable given it already receives its dependency via constructor) |
| Version catalogue | root | Add Hilt (and its annotation-processing tool) as managed dependencies |
| Build configuration | `build-logic`, module `build.gradle.kts` files | Apply Hilt's Gradle plugin and annotation processing consistently across modules that need it |

Note: the exact number and organisation of DI provisioning files (how many, what they're named, which scope annotations they carry) is an implementation decision for the propose_change phase, not specified here.

## What Must Be Provided Through the Dependency Graph

Rather than prescribing Hilt module structure, this section describes the provisioning **outcomes** required — the "what," left open on the "how":

| Dependency | Scope requirement | Resolution requirement |
|-----------|--------------------|--------------------------|
| Network client (Retrofit/OkHttp) | Single instance for the application's lifetime | Available to any module that needs to make a network call |
| `AnalyticsClient` | Single instance for the application's lifetime | Available to any module that needs to log events; must have the correct provider(s) registered for the current build type at the time it is first used |
| `ProductRepository` | No stronger than singleton; instance-per-use is acceptable if stateless | Any consumer requesting the `:domain` interface type receives a working implementation without knowing it is `ProductRepositoryImpl` |
| `ApiService` | Single instance is acceptable (stateless) | Available to whatever constructs `ProductRepositoryImpl` |
| `GetProductsUseCase` | New instance per injection point is acceptable (it is a thin, stateless wrapper) | Available to any future `ViewModel` that needs it |

## Testing

### Unit Tests

The existing unit test strategy (constructor injection with mocked collaborators, established in 1.1.1 and 1.1.2) is expected to remain unchanged for `GetProductsUseCase`, `ProductRepositoryImpl`, `AnalyticsClient`, and the analytics providers. These classes should continue to be testable by direct construction with mocked/fake dependencies — Hilt should not need to be involved to unit test business logic.

| Class Under Test | What to Test |
|-------------------|--------------|
| Any new provisioning code (e.g. functions/classes responsible for constructing the network client or `AnalyticsClient` with providers registered) | The provisioning logic produces a correctly configured instance (correct base URL, correct providers registered per build type) — testable as a plain function/class without booting the Hilt graph |
| Existing classes (`GetProductsUseCase`, `ProductRepositoryImpl`, `AnalyticsClient`, `DebugAnalyticsProvider`) | No behavioural change expected; existing tests should continue to pass unmodified, confirming Hilt adoption did not alter runtime behaviour |

### Instrumented / DI-Graph Tests

Hilt provides test-specific infrastructure (a test application class, a JUnit rule, and the ability to replace bindings) for verifying that the dependency graph itself assembles correctly and resolves to the intended types. This story should include at least one instrumented or graph-validation test that confirms:
- The application's Hilt component builds successfully (the graph has no missing or circular dependencies)
- `ProductRepository` resolves to `ProductRepositoryImpl` when requested through injection
- The debug analytics provider is registered when the graph is assembled under the debug build type

The exact mechanism (instrumented test using Hilt's test application, or a JVM-level test exercising the generated component) is an implementation decision.

### Tests NOT in Scope

- `ViewModel` injection tests — no `ViewModel` exists yet; this is covered when 1.2.x introduces them
- Tests of analytics SDK behaviour or event content — covered by 1.1.2 and feature-specific analytics stories
- UI/Compose tests — no UI exists yet in this story's scope

## Security Considerations

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Build-type-gated provider registration moving into the DI graph** | Medium | 1.1.2 established that the debug analytics provider (which writes to Logcat, readable via ADB) must never be registered in release builds. Moving registration into the dependency graph must preserve this guarantee at the build-variant level (verifiable at build/compile time), not rely on a runtime check that could be bypassed or misconfigured. This must be explicitly verified as part of this story's Definition of Done. |
| **Dependency supply chain** | Low | Hilt/Dagger are widely-used, well-audited libraries, but as with any new dependency, versions must be pinned in the version catalogue and kept current with security advisories. |
| **Expanded injection entry points** | Low | Making `MainActivity` (and, later, other Activities/Fragments) an injection entry point slightly increases the surface exposed to the DI graph. This is standard practice and low risk, but reinforces that only intended types should be exposed through the graph — internal implementation details should remain unexposed to consumers that don't need them. |
| **Generated code correctness** | Low | Hilt-generated component/factory code is not hand-written and therefore not directly reviewed. Rely on successful compilation and the DI-graph test (see Testing) as the verification mechanism rather than manual code review of generated classes. |

## Performance Considerations

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Build time impact of annotation processing** | Medium | Hilt relies on annotation processing to generate the dependency graph at compile time, which adds build time. This should be measured before/after adoption; if significant, consider whether the chosen annotation-processing mechanism (implementation decision, out of scope here) minimises the impact. |
| **Application startup cost** | Low | Singleton-scoped dependencies (network client, `AnalyticsClient`) should be constructed lazily on first use rather than eagerly at `Application.onCreate`, so DI adoption does not add measurable startup latency. This should be verified rather than assumed. |
| **No runtime injection overhead for this story's dependencies** | None expected | The dependencies covered here (`GetProductsUseCase`, `ProductRepositoryImpl`, network/analytics clients) are looked up once per consumer lifetime, not per method call, so steady-state performance should be unaffected. |

## GDPR and Sensitive Information

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Regression of the debug-provider release-safety guarantee** | Medium | This is the primary GDPR-adjacent risk of this story: 1.1.2 already established that no analytics data should be logged (even to Logcat) in release builds. Because this story changes *how* the debug provider gets registered, there is a risk of introducing a regression where it becomes registered in release builds. This must be explicitly tested (see Testing) and called out in the Definition of Done, not just assumed to carry over correctly. |
| **No new personal data introduced** | None | This story only changes how existing objects are constructed and wired; it does not introduce new data collection, storage, or transmission. No new GDPR review is required beyond re-confirming the existing 1.1.2 mitigation still holds. |

## Other Non-Functional Requirements

| Concern | Category | Mitigation |
|---------|----------|------------|
| **Consistency with the project's constructor-injection convention** | Maintainability | The Android guidelines already require dependencies to be passed via constructor. Hilt adoption should reinforce this convention (constructor-injectable classes) rather than introduce field injection except where framework constraints require it (e.g. Activities). |
| **Convention-plugin alignment** | Maintainability | The project already centralises shared build configuration through `build-logic` convention plugins. Hilt's Gradle plugin and annotation-processing configuration should be added consistently through this mechanism rather than duplicated per module, per the existing Gradle guidelines. |
| **Version catalogue discipline** | Build | All new dependencies (Hilt runtime, compiler/processor, any Hilt testing artifacts) must be declared in `gradle/libs.versions.toml` and referenced via `libs.*`, per the existing Gradle guidelines — never as hardcoded coordinates. |
| **Readiness already anticipated in build configuration** | Observation | The `:app` module's Kover configuration already excludes Hilt-generated class name patterns (`*_HiltModules*`, `hilt_aggregated_deps.*`, `dagger.hilt.*`, `*.Hilt_*`, `*.di.*`) and the `@HiltViewModel` annotation, even though Hilt is not yet applied. This confirms the project was scaffolded in anticipation of this story; the exclusions should be reviewed for correctness once Hilt is actually applied. |
| **Migration completeness** | Maintainability | `NetworkClient` currently exists as a Kotlin `object` singleton. If it is converted to an injectable type, verify no residual manual references to the old `object` API remain anywhere in the codebase. |
| **Module boundary preservation** | Architecture | Adopting Hilt must not weaken the existing Clean Architecture boundaries — in particular, `:domain` must still not gain any dependency on `:core`/`:data`/Android/Hilt framework types beyond what constructor-injection annotations minimally require. This should be explicitly checked, since DI frameworks can create pressure to leak framework annotations into places that should stay framework-agnostic. |

## Assumptions

1. No `ViewModel` currently exists in the codebase (the `:app` module contains only `MainActivity` and the theme). This story establishes DI infrastructure proactively; the literal "`@HiltViewModel` on all ViewModels" criterion is deferred to the stories that actually introduce ViewModels (1.2.x onward), which must build on this story's infrastructure.
2. The choice of annotation-processing mechanism (e.g. KSP vs. kapt) is deferred to the propose_change/implementation phase.
3. The exact number, naming, and scope structure of DI provisioning files is deferred to the propose_change phase, per the stated constraint to stay at the "what" level.
4. Whether `NetworkClient` and `ProductMapper` (currently Kotlin `object`s) are converted to constructor-injected classes or remain as objects wrapped by a provisioning function is an implementation decision.
5. Hilt's version will be chosen for compatibility with the project's current Kotlin (2.2) and AGP versions, and pinned in `gradle/libs.versions.toml`.
6. Favourites persistence DI (story 2.1.2, not yet implemented) is out of scope; this story covers only dependencies that exist in the codebase today (network client, analytics client, `ProductRepository`, `GetProductsUseCase`, `ApiService`).
7. No real analytics SDK is introduced by this story (per 1.1.2's scope) — only the debug provider's registration mechanism changes.
