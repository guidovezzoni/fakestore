# Get Products Use Case

**Epic**: 1 -- Product Catalogue
**Feature**: 1.1 -- Data Layer & Analytics Setup
**Story ID**: 1.1.1
**Role**: Developer
**Status**: Refined
**Modules created**: `build-logic`, `:core`, `:domain`, `:data`

## User Story

As a developer, I want a `GetProductsUseCase` backed by a network service that exposes `Flow<Result<List<Product>>>` so that the UI can react to loading, success, and error states.

## Description

This is the foundational data-layer story for the Product Catalogue epic. It establishes the multi-module Clean Architecture (`:core`, `:domain`, `:data`) and creates the end-to-end pipeline from the FakeStore remote API to a domain-layer use case that downstream features (Product List Screen 1.2.1, Product List States 1.2.2) will consume.

The scope covers:
- Creating a `build-logic` composite build with Gradle convention plugins to centralise shared build configuration across modules
- Creating three new Gradle modules (`:core`, `:domain`, `:data`) and wiring them in `settings.gradle.kts`
- Adding networking dependencies to the version catalogue
- Defining the `Product` domain model (pure Kotlin, no framework imports)
- Defining a DTO model matching the API response shape, with a mapper to the domain model
- Defining the `ProductRepository` interface in `:domain` and its implementation in `:data`
- Implementing `GetProductsUseCase` that returns `Flow<Result<List<Product>>>`
- Ensuring all network errors are caught at the repository boundary and surfaced as `Result.failure`

This story does NOT include UI, dependency injection wiring (see 1.1.3), or analytics (see 1.1.2).

## API Endpoint

### Get All Products

- **URL**: `GET https://fakestoreapi.com/products`
- **Authentication**: None required
- **Request body**: None
- **Rate limiting**: None documented
- **Response**: JSON array of product objects (HTTP 200)

#### Response Schema

The endpoint returns a flat JSON array of 20 product objects. There is no pagination envelope, no metadata, and no cursor -- the full catalogue is returned in a single response.

```json
[
  {
    "id": 1,
    "title": "Fjallraven - Foldsack No. 1 Backpack, Fits 15 Laptops",
    "price": 109.95,
    "description": "Your perfect pack for everyday use and walks in the forest...",
    "category": "men's clothing",
    "image": "https://fakestoreapi.com/img/81fPKd-2AYL._AC_SL1500_t.png",
    "rating": {
      "rate": 3.9,
      "count": 120
    }
  }
]
```

#### Field Definitions

| Field | JSON Type | Nullable | Notes |
|-------|-----------|----------|-------|
| `id` | number (integer) | No | Unique product identifier, range 1--20 in current dataset |
| `title` | string | No | Product name, up to ~100 characters observed |
| `price` | number (decimal) | No | Price in USD, observed range 7.95--999.99 |
| `description` | string | No | Product description, variable length |
| `category` | string | No | One of: `"men's clothing"`, `"women's clothing"`, `"jewelery"`, `"electronics"` |
| `image` | string (URL) | No | HTTPS URL pointing to a product image |
| `rating.rate` | number (decimal) | No | Average rating, observed range 1.9--4.8 |
| `rating.count` | number (integer) | No | Number of ratings, observed range 70--679 |

> **Note**: The API is a fake/test API. Field nullability is based on observation of the current 20-product dataset, not formal documentation. The DTO should defensively handle potentially missing or null fields.

## Data Models

### Domain Model: `Product`

Pure Kotlin data class in `:domain`. No Android, networking, or serialisation framework imports.

| Field | Kotlin Type | Maps From | Notes |
|-------|-------------|-----------|-------|
| `id` | `Int` | `id` | Unique identifier |
| `title` | `String` | `title` | Product name |
| `price` | `Double` | `price` | Price in USD |
| `description` | `String` | `description` | Full description text |
| `category` | `String` | `category` | Category name |
| `imageUrl` | `String` | `image` | Product image URL |
| `rating` | `Rating` | `rating` | User rating (value object) |

The domain model keeps `Rating` as a separate value object rather than flattening it into top-level fields. `Rating` is a meaningful domain concept (a score paired with a count) and preserving it as a value object keeps the model expressive and easier to extend.

### Domain Model: `Rating`

Pure Kotlin data class in `:domain`. A value object representing a product's user rating.

| Field | Kotlin Type | Maps From | Notes |
|-------|-------------|-----------|-------|
| `score` | `Double` | `rating.rate` | Average user rating |
| `count` | `Int` | `rating.count` | Number of user ratings |

### DTO Model: `ProductDto`

Data class in `:data` annotated for JSON deserialisation. Mirrors the API response shape exactly, including the nested `RatingDto` object.

| Field | Kotlin Type | JSON Key |
|-------|-------------|----------|
| `id` | `Int` | `id` |
| `title` | `String` | `title` |
| `price` | `Double` | `price` |
| `description` | `String` | `description` |
| `category` | `String` | `category` |
| `image` | `String` | `image` |
| `rating` | `RatingDto` | `rating` |

### DTO Model: `RatingDto`

| Field | Kotlin Type | JSON Key |
|-------|-------------|----------|
| `rate` | `Double` | `rate` |
| `count` | `Int` | `count` |

### Mapper: `ProductDto` to `Product`

A mapper in `:data` converts `ProductDto` (and its nested `RatingDto`) to the `Product` domain model (and its nested `Rating` value object). The mapper must:
- Map `RatingDto` to the `Rating` domain value object
- Not be accessible from `:domain` (it belongs in the data layer)

## Repository Contract

### Interface: `ProductRepository` (in `:domain`)

```kotlin
interface ProductRepository {
    suspend fun getProducts(): List<Product>
}
```

- Returns domain models only -- no DTOs cross the domain boundary
- Throws on network/parsing failure; the use case wraps in `Result`

### Implementation: `ProductRepositoryImpl` (in `:data`)

- Calls the API service to fetch `List<ProductDto>`
- Applies the mapper to convert each DTO to a `Product`
- Returns `List<Product>`

## Use Case Contract

### `GetProductsUseCase` (in `:domain`)

```kotlin
class GetProductsUseCase(private val repository: ProductRepository) {
    operator fun invoke(): Flow<Result<List<Product>>>
}
```

- Emits a single `Result.success` containing the product list on success
- Emits `Result.failure` wrapping the caught exception on any error
- No unhandled exceptions escape to the caller

## Convention Plugins

### Overview

To avoid duplicating build configuration (compile options, detekt, kover, SDK versions) across the new modules, a `build-logic` composite build provides Gradle convention plugins. Each convention plugin encapsulates a reusable build configuration that modules opt into by applying the plugin in their `build.gradle.kts`.

### Structure

The convention plugins live in a `build-logic` directory at the project root, included as a composite build in `settings.gradle.kts` via `pluginManagement { includeBuild("build-logic") }`. The `build-logic` module uses the `kotlin-dsl` plugin to define convention plugins as Kotlin classes.

```
build-logic/
├── build.gradle.kts          # kotlin-dsl plugin, dependencies on AGP and Kotlin plugin artifacts
├── settings.gradle.kts        # dependencyResolutionManagement pointing to the root version catalogue
└── src/main/kotlin/
    ├── AndroidLibraryConventionPlugin.kt   # com.android.library + shared Android config
    └── KotlinLibraryConventionPlugin.kt    # kotlin("jvm") for pure Kotlin modules
```

### Convention Plugin Definitions

#### `AndroidLibraryConventionPlugin`

- **Plugin ID**: registered in `build-logic/build.gradle.kts` via `gradlePlugin { plugins { ... } }` (e.g. `fakestore.android.library`)
- **Applies**: `com.android.library`, `org.jetbrains.kotlin.android`, detekt, kover
- **Configures**:
  - `compileSdk`, `minSdk`, `targetSdk` matching the app module's values
  - `compileOptions` (Java 11 source/target compatibility)
  - `kotlinOptions` (`jvmTarget = "11"`)
  - Detekt with the project's `detekt.yml` and `buildUponDefaultConfig = true`
  - Kover exclusion filters and 95% minimum bound (matching the app module's configuration)
- **Used by**: `:core`, `:data` (and `:app` can migrate to it in a follow-up)

#### `KotlinLibraryConventionPlugin`

- **Plugin ID**: e.g. `fakestore.kotlin.library`
- **Applies**: `kotlin("jvm")`, detekt, kover
- **Configures**:
  - `jvmTarget = "11"`
  - Detekt with the project's `detekt.yml` and `buildUponDefaultConfig = true`
  - Kover exclusion filters and 95% minimum bound
- **Used by**: `:domain`

### Version Catalogue Access

The `build-logic` module accesses the root project's `gradle/libs.versions.toml` version catalogue through `dependencyResolutionManagement` in `build-logic/settings.gradle.kts`:

```kotlin
dependencyResolutionManagement {
    repositories {
        google()
        mavenCentral()
        gradlePluginPortal()
    }
    versionCatalogs {
        create("libs") {
            from(files("../gradle/libs.versions.toml"))
        }
    }
}
```

This ensures a single source of truth for all dependency versions across both the main project and the convention plugins.

### Module `build.gradle.kts` Simplification

With convention plugins, individual module build files become minimal. For example:

```kotlin
// data/build.gradle.kts
plugins {
    alias(libs.plugins.fakestore.android.library)
}

android {
    namespace = "com.guidovezzoni.fakestore.data"
}

dependencies {
    implementation(project(":domain"))
    implementation(project(":core"))
    // module-specific dependencies only
}
```

## Security Considerations

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Unencrypted network traffic** | Medium | The base URL uses HTTPS. Ensure the network client does not allow cleartext fallback. Android's `NetworkSecurityConfig` should block cleartext by default on API 24+ (the project's `minSdk`). |
| **Base URL hardcoding** | Low | The base URL `https://fakestoreapi.com` should be externalised (e.g. via `BuildConfig` field or a configuration provider) so it can be overridden per build variant and is not scattered across the codebase. |
| **Certificate pinning** | Low | Not required for a test/demo API. Note as a future consideration if the app connects to a production API. |
| **Sensitive data in logs** | Low | Ensure the network client does not log request/response bodies in release builds. Logging interceptors, if added, must be limited to debug builds. |
| **Dependency supply chain** | Low | Pin exact versions of networking libraries in the version catalogue. Review transitive dependencies. |

## Performance Considerations

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Network call on main thread** | High | The repository's `suspend` function and the use case's `Flow` ensure the network call runs off the main thread. Acceptance criteria verify this through the coroutine-based API. |
| **No caching** | Medium | The current scope loads products fresh on every call. This is acceptable for 20 items but should be noted as a candidate for caching (in-memory or HTTP-level) in a future story if the catalogue grows. |
| **Large response payload** | Low | The API returns all 20 products (~15 KB). No risk at current dataset size. The story notes pagination-readiness in the technical notes -- a future concern if the API grows. |
| **Image URL loading** | Low | This story only fetches product metadata (URLs). Actual image loading and caching is the UI layer's concern (story 1.2.1). |
| **JSON parsing overhead** | Low | 20 small objects is negligible. No special handling needed. |

## GDPR and Sensitive Information

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Personal data in product data** | None | The `/products` endpoint returns only product catalogue data (titles, prices, descriptions, images, ratings). No PII (names, emails, addresses) is present in the response. |
| **User tracking via network requests** | Low | The API call itself does not send any user identifiers. However, the user's IP address is visible to the API server. This is inherent to any network request and does not require mitigation at this layer. Note: analytics tracking is a separate concern (story 1.1.2). |
| **Data storage** | None | This story does not persist any data locally. Products are held only in memory. If caching is added in the future, a GDPR review should be performed at that time. |
| **Third-party data processing** | Low | `fakestoreapi.com` is a third-party test API. For a production app, the privacy policy should disclose data sent to third-party APIs. For this demo/interview context, no action required. |

## Other Non-Functional Requirements

| Concern | Category | Mitigation |
|---------|----------|------------|
| **Network timeout** | Reliability | The network client should be configured with reasonable connect and read timeouts (e.g. 10--30 seconds). Without explicit timeouts, a hanging connection blocks the coroutine indefinitely. |
| **Offline behaviour** | Reliability | When there is no network connectivity, the use case must emit `Result.failure` with a meaningful exception. The UI layer (story 1.2.2) will handle showing an error state. |
| **Proguard / R8 rules** | Build | DTO classes must not be obfuscated if reflection-based JSON parsing is used. Ensure keep rules are in place or use a code-generation-based serialisation approach. |
| **Module isolation** | Maintainability | `:domain` must remain a pure Kotlin module with no Android dependencies. This should be enforced by using the `kotlin("jvm")` plugin (not `com.android.library`) for `:domain`. |
| **Thread safety** | Reliability | The repository and use case must be safe to call from any coroutine context. They should not hold mutable shared state. |
| **API versioning** | Maintainability | The FakeStore API has no versioning scheme. The DTO should defensively handle unexpected fields (ignore unknown fields in the JSON parser configuration). |
| **Testability** | Maintainability | All dependencies are passed via constructor injection. Repository implementations depend on interfaces, not concrete classes. |

## Assumptions

1. The FakeStore API (`https://fakestoreapi.com/products`) remains available and returns the documented 20-product JSON array. It is a public test API with no SLA.
2. The `:domain` module will use the `kotlin("jvm")` Gradle plugin (pure Kotlin, no Android framework). The `:core` and `:data` modules may use `com.android.library` if needed for Android-specific networking configuration.
3. The specific networking and JSON serialisation libraries will be chosen during the implementation/proposal phase -- this story intentionally does not prescribe them.
4. The `Page<T>` wrapper mentioned in the original technical notes is a future-proofing concern. For this story, the repository returns `List<Product>` directly. Pagination readiness is deferred until an API with pagination metadata is introduced.
5. Dependency injection wiring is out of scope (covered in story 1.1.3). The classes in this story accept dependencies via constructor parameters.
6. MockK is used for test mocking, consistent with the project test dependencies (to be added to the version catalogue).
7. All field values from the API are treated as non-null based on observation of the current dataset; however, the DTO layer should handle missing fields defensively.
