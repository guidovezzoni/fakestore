# Favourites Screen

**Epic**: 2 -- Favourites Management
**Feature**: 2.2 -- Favourites Screen
**Story**: 2.2.1 -- Favourites Screen
**Modules**: `:app`, `:core`

---

## Description

The Favourites screen allows users to view and manage the products they have saved as favourites. It is accessible via the bottom navigation bar and displays only the subset of products whose IDs are persisted in the local Room database. The screen reuses the same card layout as the Products screen (`ProductListItemCard`) so the experience feels consistent. Users can remove a favourite directly from this screen, which immediately updates the displayed list.

The screen must also track an analytics event (`favourites_screen_viewed`) each time it enters composition, including the count of favourites at load time as a parameter.

The Favourites feature is **local-only** -- there is no remote endpoint for favourites. The screen combines the full product list (fetched via `GetProductsUseCase` from the Fake Store API) with the favourite IDs (from Room via `GetFavouriteIdsUseCase`) to build its display list. No separate API call is needed.

**Current implementation status**: The FavouritesScreen composable, FavouritesViewModel, and MVI artefacts (state, intent, effect) already exist from story 2.1.1. This story addresses the remaining gaps: the `favourites_screen_viewed` analytics event (with `favourite_count` parameter), an enriched empty-state message, and ensuring full test coverage for all Favourites screen behaviour.

---

## User Stories

**As a user**, I want a Favourites screen showing only my saved products so that I can review them quickly.

**As a product owner**, I want a `favourites_screen_viewed` analytics event (with `favourite_count`) logged each time the Favourites screen is viewed, so that engagement with the Favourites feature is measurable.

## Acceptance Criteria

### Display
- [ ] The Favourites screen displays only products whose IDs are in the Room database
- [ ] Cards use the same layout as the Products screen (`ProductListItemCard`): product name, image, price, rating score, and favourite toggle icon
- [ ] All items on the Favourites screen show a **filled** heart icon (they are all favourites by definition)

### Remove behaviour
- [ ] Removing a favourite from this screen removes it immediately from the displayed list (optimistic update)
- [ ] If the underlying database write fails, the UI reverts to the previous state and the user is notified via a snackbar ("Unable to update favourite")
- [ ] On successful removal, a `favourite_removed` analytics event is logged with `product_id` param (already implemented in 2.1.1)

### Navigation
- [ ] The screen is reachable via the bottom navigation bar (Favourites tab with heart icon)
- [ ] The Favourites tab is the second item in the bottom navigation bar

### Empty state
- [ ] When the favourites list is empty, a descriptive message is shown centred on screen
- [ ] The empty-state message reads: "No favourites yet. Tap the heart on a product to save it."
- [ ] The empty state is shown both on first launch (no favourites saved) and after the user removes all favourites

### Loading state
- [ ] While products are being fetched, a centred loading indicator is shown

### Error state
- [ ] If the product list fails to load, a centred error message is shown ("Something went wrong. Please try again.")

### Analytics
- [ ] `favourites_screen_viewed` is logged once each time the Favourites screen enters composition
- [ ] The event includes a `favourite_count` parameter (Int) reflecting the number of favourite items shown at load time
- [ ] The event follows the same pattern as `product_list_viewed`: a `LaunchedEffect(Unit)` triggers a ViewModel intent, and the ViewModel logs the event once data is available
- [ ] The analytics event is NOT logged if the screen is in an error state (no data to report)

### Consistency
- [ ] The favourite state is consistent between the Products screen and the Favourites screen -- toggling on one is reflected on the other via the shared Room-backed `Flow` of favourite IDs

## Data Model

### No new domain models or entities required

The existing data model is sufficient:
- **`FavouriteEntity`** (Room, `:data`): stores `productId` (Int, primary key)
- **`Product`** (domain): full product data from the API
- **`ProductListItem`** (UI state): display model with `id`, `imageUrl`, `title`, `formattedPrice`, `formattedRatingScore`, `isFavourite`

### UI State (existing)

`FavouritesUiState` is a sealed interface with three variants:

| Variant | Fields | Notes |
|---------|--------|-------|
| `Loading` | -- | Initial state while products are being fetched |
| `Content` | `products: List<ProductListItem>` | Filtered list of favourited products |
| `Error` | -- | Product list fetch failed |

No changes to the state structure are needed.

### UI Intent (update required)

`FavouritesUiIntent` currently has:

| Entry | Notes |
|-------|-------|
| `LoadFavourites` | Triggers product list fetch |
| `ToggleFavourite(productId: Int)` | Removes a favourite from the screen |

**Add:**

| Entry | Notes |
|-------|-------|
| `TrackScreenViewed` | Signals the ViewModel to log the `favourites_screen_viewed` analytics event |

### UI Effect (no changes)

`FavouritesUiEffect` currently has `ShowFavouriteToggleError`. No additions needed.

### Analytics Event

| Event Name | Parameters | When Logged |
|------------|-----------|-------------|
| `favourites_screen_viewed` | `favourite_count` (Int) | Once per screen composition, after content is available |

## Endpoints / Data Sources

### Remote API
No changes. The existing `ApiService.getProducts()` (`GET /products` on `https://fakestoreapi.com`) remains the sole source of product data. No new endpoints are required.

### Local Database (Room)
No changes. The existing `FavouriteDao` and `FavouritesDatabase` provide all necessary operations:
- `getAllIds(): Flow<List<Int>>` -- reactive stream of favourite product IDs
- `insert(entity: FavouriteEntity)` -- add a favourite
- `delete(entity: FavouriteEntity)` -- remove a favourite

## Security Concerns and Mitigations

| Concern | Risk | Mitigation |
|---------|------|------------|
| Analytics event data exposure | Low -- `favourites_screen_viewed` contains only `favourite_count` (an integer count). No product IDs, user identifiers, or PII are included in this event. | Ensure the event params contain only `favourite_count` (Int). Never add user identifiers or product details to this event. |
| Favourite product IDs in Room database | Low -- already assessed in story 2.1.1. Only integer product IDs are stored; no PII. | No additional action needed. |
| Network request for product data | Low -- the product list is fetched over HTTPS from `fakestoreapi.com`. | The existing `NetworkClient` in `:core` uses OkHttp with HTTPS. No changes needed. |

## Performance Concerns and Mitigations

| Concern | Risk | Mitigation |
|---------|------|------------|
| Fetching the full product list to display a small subset of favourites | Medium -- if the product catalogue grows significantly, fetching all products just to display a few favourites becomes wasteful. | For the current scope (~20 products from Fake Store API), this is acceptable. If the product count grows, consider caching the product list or fetching only favourited products. This is out of scope for this story. |
| Redundant product list fetch across screens | Low -- both ProductListScreen and FavouritesScreen independently call `GetProductsUseCase`. | Each screen's ViewModel has its own lifecycle. The second fetch may hit cache (if implemented) or make a redundant API call. For ~20 products, the impact is negligible. A shared repository cache is a potential future optimisation but out of scope. |
| Combining product list with favourite IDs on every Room emission | Low -- Room emits only when the favourites table changes. The combination is O(n) with n ~20. | No mitigation needed at current scale. |
| LazyColumn key stability | Low | Items are keyed by `it.id` (product ID), which is stable. This ensures efficient recomposition when the list changes. Already implemented. |

## GDPR and Sensitive Information

| Concern | Assessment | Mitigation |
|---------|------------|------------|
| Personal data in favourites | **No PII is stored.** The favourites table contains only integer product IDs. No user account, name, email, or behavioural profile is persisted. | No GDPR data subject rights (access, erasure, portability) apply to this data in isolation. |
| `favourites_screen_viewed` analytics event | **No PII.** The event contains only `favourite_count` (an anonymous integer). Without a user identifier, individual preferences cannot be reconstructed. | If a user identifier is added to analytics in the future, a privacy impact assessment should be conducted. For now, events are anonymous. |
| Behavioural inference from favourite count | **Negligible.** A raw count of favourites without user identification or product details provides no meaningful personal insight. | No mitigation required. |
| Data retention | Favourites persist on-device indefinitely until the user uninstalls or clears app data. | Standard behaviour for local preferences. No server-side retention concerns since data is not synced. |
