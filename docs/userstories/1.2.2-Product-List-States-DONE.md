# Product List States

**Epic**: 1 — Product Catalogue
**Feature**: 1.2 — Product List Screen
**Modules**: `:app`

## User Story

As a user, I want loading, error (with retry), and empty states so that I always know what the app is doing.

## Description

The product list screen currently displays product cards when data is available but has no handling for loading, error, or empty states. This story introduces three distinct visual states so the user always has clear feedback about what the app is doing:

1. **Loading state**: While the network call to `GET /products` is in flight, the screen displays a full-screen loading indicator (centred spinner) instead of the product list. This replaces the current behaviour where the screen is blank during loading.

2. **Error state**: When the network call fails (timeout, no connectivity, server error, malformed response), the screen displays a full-screen error message with a "Retry" button. Tapping "Retry" re-triggers the product-fetch use case. The error message should be user-friendly and not expose technical details (no stack traces, no HTTP status codes, no exception class names).

3. **Empty state**: When the API returns a successful response with an empty product list (`[]`), the screen displays an empty-state message informing the user that no products are available.

The current `ProductListUiState` is a flat data class with a single `products` field. It needs to be restructured as a sealed type with exactly three variants (`Loading`, `Content`, `Error`) to enforce mutual exclusivity of states -- it should be impossible to represent an invalid combination (e.g. "loading" and "showing products" simultaneously).

## Endpoint

| Method | URL | Current usage |
|--------|-----|---------------|
| `GET` | `https://fakestoreapi.com/products` | Already implemented in `ApiService.getProducts()`. No endpoint changes required. |

The API returns `200 OK` with `application/json`. A successful response is a JSON array of product objects. An empty catalogue returns `[]`. Error cases surface as HTTP error codes or network-level failures (timeouts, DNS, connection refused).

- [ ] **AC-2**: When the product list is loading, no product cards or other content are visible -- only the loading indicator

### ViewModel tests (extend existing `ProductListViewModelTest.kt`)

## Security

| Concern | Risk | Mitigation |
|---------|------|------------|
| Error message information leakage | Low | The error state must display a generic, user-friendly message. Exception class names, HTTP status codes, server hostnames, and stack traces must never be shown to the user. Log technical details at debug level only. |
| API response injection | Low | The app already uses kotlinx-serialization with strict typing. No raw HTML or JS is rendered from API responses. Compose text rendering does not interpret markup. No additional mitigation needed. |
| Retry abuse (unintentional DoS) | Very low | The Retry button triggers a single network call. There is no auto-retry loop. The existing OkHttp timeouts (10s connect, 30s read) bound each attempt. No rate-limiting is required for this story, but consider it if auto-retry or pull-to-refresh are added later. |

## Performance

| Concern | Risk | Mitigation |
|---------|------|------------|
| Rapid retry tapping | Low | Each `RetryClicked` intent triggers a new coroutine. If the user taps retry rapidly, multiple concurrent fetches could run. Consider cancelling in-flight requests when a new fetch starts (e.g. using a single coroutine job reference or `collectLatest`). |
| Unnecessary recomposition | Low | The sealed type approach naturally limits recomposition -- only the branch matching the current state variant is composed. Using `StateFlow` with structural equality ensures recomposition only on actual state changes. |
| No caching | Informational | This story does not introduce caching. Every retry is a fresh network call. This is acceptable for the current scope but should be revisited if the product list grows large or the API becomes slow. |

## GDPR and Sensitive Information

| Concern | Risk | Mitigation |
|---------|------|------------|
| Personal data exposure | None | The Fake Store API returns only product catalogue data (titles, prices, descriptions, images, ratings). No personal data, user identifiers, or tracking information is involved in this feature. |
| Error logging | Very low | If error details are logged for debugging, ensure logs do not capture request headers that might contain authentication tokens or user identifiers. The current implementation does not use authentication, so this is not an immediate risk but should be considered if auth is added. |
| Analytics tracking | Very low | If analytics events are added for state transitions (loading, error, retry), ensure they do not include any user-identifying information beyond what is already consented to. The existing `AnalyticsClient` abstraction should be reviewed before adding any new events. |

## Other Non-Functional Requirements

| Concern | Risk | Mitigation |
|---------|------|------------|
| Accessibility | Medium | The loading indicator, error message, retry button, and empty-state message must all have appropriate content descriptions for screen readers. The retry button must be focusable and activatable via accessibility services. Use semantic Compose modifiers. |
| Localisation | Low | All new user-facing strings must be extracted to `strings.xml` and translated in existing locale directories (`values-es`). Use the ellipsis character where applicable, not three dots. |
| Offline behaviour | Informational | This story covers the error state when the network call fails, which includes offline scenarios. No specific offline-first or cached fallback behaviour is in scope. The error state with retry is the offline experience. |
| State persistence across configuration changes | Low | `StateFlow` in the ViewModel already survives configuration changes (e.g. rotation). The sealed state approach does not change this. However, if the screen is in `Loading` state during a configuration change, the fetch should not restart -- the existing coroutine in `viewModelScope` handles this. |
| Testability | Low | The sealed type is easier to test exhaustively than the current flat data class. The `when` expression on the sealed type in the composable will produce a compile error if a new variant is added without handling it, preventing regressions. |
