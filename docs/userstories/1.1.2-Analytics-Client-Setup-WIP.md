# Analytics Client Setup

**Epic**: 1 -- Product Catalogue
**Feature**: 1.1 -- Data Layer & Analytics Setup
**Story ID**: 1.1.2
**Role**: Developer
**Status**: Refined
**Modules**: `:core`

## User Story

As a developer, I want an analytics client set up in `:core` so that any module can log events without knowing the underlying SDK.

## Description

This story establishes the analytics abstraction layer for the FakeStore application. It creates an interface in the `:core` module that all feature modules use to log analytics events, decoupling the rest of the codebase from any specific analytics SDK (Firebase Analytics, Mixpanel, Amplitude, etc.).

The scope covers:
- Defining an `AnalyticsClient` interface in `:core` with a single method for logging named events with optional key-value parameters
- Providing a debug implementation that logs events to Logcat (usable during development)
- Providing a no-op implementation that silently discards events (usable in release builds until a real SDK is integrated)
- Unit tests for both implementations

This story does NOT include:
- Hilt/DI wiring of the analytics client (see story 1.1.3)
- Actual analytics SDK integration (Firebase, Mixpanel, etc.) -- this is deferred until an SDK decision is made
- Consent management or opt-out mechanisms -- these will be required when a real SDK is introduced
- Defining specific analytics event names or parameters -- those are defined per-feature in stories 1.2.4, 2.1.3, 2.2.3, and 3.1.4

### Downstream Consumers

The following stories depend on this analytics interface:
- **1.2.4** Product List Analytics: `product_list_viewed` (no params)
- **2.1.3** Favourite Toggle Analytics: `favourite_added` / `favourite_removed` (with `product_id` param)
- **2.2.3** Favourites Screen Analytics: `favourites_screen_viewed` (with `favourite_count` param)
- **3.1.4** Profile Screen Analytics: `profile_screen_viewed` (no params)

All downstream stories reference `:core` for the analytics client and pass event data as `Map<String, Any>`.

## Interface Contract

### `AnalyticsClient` (in `:core`)

```kotlin
interface AnalyticsClient {
    fun logEvent(name: String, params: Map<String, Any> = emptyMap())
}
```

| Parameter | Type | Description |
|-----------|------|-------------|
| `name` | `String` | Event name (e.g. `"product_list_viewed"`, `"favourite_added"`). Non-empty. |
| `params` | `Map<String, Any>` | Optional key-value pairs providing context for the event (e.g. `"product_id" to 42`). Values are expected to be primitives (`String`, `Int`, `Long`, `Double`, `Boolean`). Defaults to an empty map. |

Design rationale:
- The `fun` (not `suspend fun`) signature keeps the interface simple -- analytics logging is fire-and-forget and must not block callers. Implementations that need asynchronous I/O (e.g. batching to a network endpoint) manage their own concurrency internally.
- The `Map<String, Any>` parameter type provides flexibility for any event schema without requiring callers to depend on SDK-specific parameter builders.

### Implementations

#### Debug Implementation

A concrete implementation for debug builds that formats the event name and parameters into a human-readable string and writes it to Logcat. This allows developers to verify analytics instrumentation during development without a real analytics backend.

Observable behaviour:
- Each `logEvent` call produces a single Logcat entry at the DEBUG level
- The log entry includes the event name and all parameter key-value pairs
- An event with no parameters still produces a log entry (with just the event name)

#### No-Op Implementation

A concrete implementation for release builds (or when analytics is disabled) that does nothing. All method calls are silently ignored.

Observable behaviour:
- `logEvent` returns immediately with no side effects
- No exceptions are thrown regardless of input

| Class Under Test | What to Test |

## Security Considerations

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Sensitive data leakage via event parameters** | Medium | The `Map<String, Any>` parameter type is intentionally flexible but creates risk that callers could inadvertently pass PII (emails, names, addresses) or sensitive data (tokens, passwords) as event parameters. Mitigation: document clearly in the interface KDoc that event parameters must never contain PII or credentials. Feature stories that define specific events must specify allowed parameters explicitly. When a real SDK is integrated, consider adding a parameter validation/sanitisation layer. |
| **Debug logging on production devices** | Medium | The debug implementation writes event data to Logcat, which is accessible on rooted devices and via ADB. Mitigation: the DI wiring (story 1.1.3) must ensure the debug implementation is only used in debug builds, never in release. The no-op implementation should be the release default until a real SDK is integrated. |
| **Log injection** | Low | Malicious or malformed event names/parameters could produce misleading log output. Severity is low since Logcat is a development tool, not a production logging pipeline. No mitigation required at this stage. |

## Performance Considerations

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **Blocking the calling thread** | Medium | The `logEvent` method is a synchronous (non-suspend) call. The debug implementation writes to Logcat, which is effectively instantaneous. The no-op implementation is a no-op. When a real SDK is integrated, it must manage its own background threading internally (most analytics SDKs do this). The interface intentionally avoids `suspend` to keep callers simple. |
| **High-frequency event logging** | Low | If a caller logs events in a tight loop (e.g. on every recomposition), this could produce excessive Logcat output in debug. Mitigation: downstream stories specify that events are logged once per screen visit or user action, not on every recomposition. No rate-limiting is needed at the interface level for current usage patterns. |

## GDPR and Sensitive Information

| Concern | Severity | Mitigation |
|---------|----------|------------|
| **PII in analytics events** | High | The flexible `Map<String, Any>` parameter type means there is no compile-time enforcement preventing callers from including PII in event parameters. While the current downstream events only use product IDs and counts (not PII), the interface does not structurally prevent misuse. Mitigation: (1) Document in the interface that PII must never be included in event parameters. (2) Each feature story that defines analytics events must explicitly list allowed parameters and confirm no PII is included. (3) When a real analytics SDK is integrated, a GDPR review must be performed covering: consent collection, data retention, data subject access/deletion requests, and the third-party SDK's data processing agreement. |
| **Consent management** | Medium | GDPR (and ePrivacy) requires user consent before tracking analytics in most jurisdictions. This story sets up the infrastructure only; no data leaves the device (debug logs to Logcat, no-op discards). However, when a real SDK is wired in, consent must be obtained before calling `logEvent`. Mitigation: note this as a prerequisite for any real SDK integration story. The `AnalyticsClient` interface could be extended with an enable/disable mechanism at that point, or a consent-aware wrapper could be introduced. |
| **Data minimisation** | Low | The current downstream events log only event names, product IDs, and counts -- no personal data. The interface design supports data minimisation by making parameters optional and explicitly named. No mitigation needed at this stage. |

## Other Non-Functional Requirements

| Concern | Category | Mitigation |
|---------|----------|------------|
| **Thread safety** | Reliability | Both implementations must be safe to call from any thread or coroutine context. The debug implementation writes to Logcat (which is thread-safe). The no-op implementation has no state. No mutable shared state should be introduced. |
| **SDK swappability** | Maintainability | The primary purpose of this abstraction is to allow swapping the underlying analytics SDK without touching feature code. The interface must remain minimal and SDK-agnostic. When a real SDK is introduced, only a new implementation and DI binding need to change -- no feature modules should be affected. |
| **Event name conventions** | Maintainability | While this story does not define specific events, it should document the expected event naming convention (e.g. `snake_case`, matching the convention used in downstream stories: `product_list_viewed`, `favourite_added`, etc.). This avoids inconsistency as events are added across features. |
| **Parameter value types** | Reliability | The interface accepts `Map<String, Any>`, but real analytics SDKs typically support only a limited set of value types (String, Int, Long, Double, Boolean). The KDoc should document the expected parameter value types to prevent callers from passing complex objects (lists, maps, custom classes) that a future SDK implementation could not handle. |
| **Testability in consumer modules** | Maintainability | Feature modules testing their analytics instrumentation need to be able to substitute a test double for `AnalyticsClient`. The interface design naturally supports this (any test can create a mock or a simple collecting implementation). No additional work needed in this story. |
| **Kover exclusions** | Build | If the no-op implementation is trivially empty, consider whether it inflates or deflates coverage metrics. The existing Kover configuration should handle this correctly, but verify during implementation. |

## Assumptions

1. The `:core` module already exists and applies the `fakestore.android.library` convention plugin (confirmed -- it currently contains `NetworkClient`).
2. No external analytics SDK is added in this story. The debug implementation uses Android's built-in `android.util.Log` (already available in the `:core` Android library module).
3. DI wiring (binding the interface to the appropriate implementation per build type) is out of scope -- it is handled in story 1.1.3. This story creates the interface and both implementations; 1.1.3 wires them.
4. The `logEvent` method is synchronous (non-suspend). This is intentional: analytics logging is fire-and-forget, and keeping it non-suspend simplifies call sites. A future SDK integration may introduce internal async behaviour, but the interface contract remains synchronous.
5. No test dependencies beyond JUnit 4 (already in `:core`) are expected for this story. If the debug implementation requires mocking `android.util.Log`, MockK or Robolectric may be needed and should be added to the version catalogue at that point.
6. Event names follow `snake_case` convention as established by the downstream stories.
